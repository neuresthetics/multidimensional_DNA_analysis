### Pros and Cons of Processing Edge Files in Batches of Different Sizes

Processing the edge files (`edges_part1.csv` through `edges_part10.csv`) in "heavy mode" implies a thorough, resource-intensive approach: loading into a directed graph (using NetworkX as in the framework), validating indices against `nodes.csv`, extracting AD-relevant subgraphs, computing metrics like centrality or pathways, extracting invariants, and potentially integrating with bio simulations (e.g., parameterizing ODEs based on edge counts or relations). Since we "have all the time in the world," time efficiency is deprioritized in favor of depth—e.g., running recursive validations, full graph traversals, or multiple centrality types per batch.

Each file is large (~50,000–53,000 edges, ~9–10 MB based on truncated character counts), with diverse relations (e.g., PPI in part1, disease-protein in part3, anatomy-protein in part5). Processing in batches means concatenating files into a single DataFrame/graph per run, then analyzing. Below, I outline pros/cons for batch sizes of 1, 2, 3, 5, and 10 files, focusing on key factors: memory/resource usage, time/complexity, error handling, analysis quality, and scalability. These are based on the framework's design (e.g., batch_size=50 in EdgeHandler, but scaled to file-level).

- **Start small (1-2 files)** for initial testing/error hunting, then scale to 3-5 for balanced heavy-mode insights.
- **If resources allow**, aim for 5+ to maximize AD project value (e.g., grounding invariants in 2025 citations from ode_readme).
